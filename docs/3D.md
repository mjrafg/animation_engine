# 3D support (hybrid 2D + 3D)

The engine now makes **3D scenes** next to its 2D scenes. Both kinds share:

- the workspace, the asset ids and the timeline (same keyframes, interpolations and atomic `timeline_apply`);
- audio, artifacts, render jobs and the FFmpeg encoder;
- the error model and the MCP server.

A 2D scene can be drawn **on top of** a 3D scene (hybrid overlay), so 2D titles and graphics can sit over 3D renders.

Nothing about 2D changed. Existing scene files, tools and tests work as before; the 83 original
tests still pass unchanged.

```text
            ┌──────────────── engine (TypeScript): owns scene + timeline ───────────────┐
 agent ──►  │ Scene3D JSON ─► validate (assets, clips, bones, morphs, parents, tracks)  │
 (MCP)      │      └─► evaluate(frame): transforms, clip + clip time + blend weight,    │
            │          morph weights, camera/lookAt, lights, world  (per frame, baked)  │
            └───────────────────────────────┬───────────────────────────────────────────┘
                                            │ job.json (static structure + baked frame states)
                               ┌────────────▼─────────────┐
                               │ Blender (headless) only  │  engine3d.py: import GLBs, pose
                               │ DRAWS / MEASURES states  │  skeletons from the given clip
                               └────────────┬─────────────┘  times, render PNG / measure
              frame PNGs ─► (+ 2D overlay scene frame) ─► FFmpeg (+ scene audio) ─► MP4
```

Blender never decides anything about timing. For every frame the engine computes:

- which clip or clips play on each character, at which clip time and with which crossfade weight;
- every transform, morph weight, camera value and light value.

The Blender script applies that state and draws it. The agent never sees Blender, Python or FFmpeg.

## Linux installation

Tested on Ubuntu 24.04 (x86-64), Node 22, **Blender 4.0.2 from apt**.

```bash
# 3D backend (optional: without it 2D works unchanged and 3D calls return
# ENGINE_CAPABILITY_UNAVAILABLE)
sudo apt install blender python3-numpy          # numpy: needed by Blender's glTF importer
# fast renderer (EEVEE) on a headless server: EGL + Mesa (software GL if there is no GPU)
sudo apt install libegl1 libegl-mesa0 libgl1-mesa-dri

npm ci && npm run build:mcp                     # also copies engine3d.py to dist/blender/
node dist/video-engine-mcp.mjs --self-test      # checks.threeD: "Blender 4.0.2 ...; renderer: eevee (EGL); test render ok"
```

- **Blender version:** 4.0.2 is what was tested. Any 3.6 or newer is accepted; older versions are refused with a clear error. 4.2+ renamed EEVEE ("EEVEE Next"); the script handles the new name, but 4.2+ is **not tested**.
- **Official build:** instead of apt you can use the official tarball from blender.org and set `BLENDER_PATH=/opt/blender/blender`. Its bundled Python already has numpy.
- **Finding Blender:** `BLENDER_PATH`, otherwise `blender` on `PATH`.
- **Tandem:** gives the MCP server only `PATH` and `HOME` plus the integration env, so either install Blender on the system `PATH` or pass `BLENDER_PATH` when registering (`integrations/tandem/register.mjs` forwards it).
- **Health:** `engine_health` (and `--self-test`) reports `threeD` separately. A missing Blender does not make the server unhealthy for 2D. `deep:true` renders a tiny 3D frame.

### GPU / CPU

| Renderer | When | Needs | Measured here (4 CPU cores, no GPU, 1280×720, living-room scene) |
|---|---|---|---|
| **EEVEE** (default) | whenever it works on the machine (probed once per server process) | EGL/OpenGL. On a GPU machine it uses the GPU driver; without a GPU, Mesa llvmpipe software GL | draft **1.5 s**/frame, standard **3.2 s**, high (AO, larger shadow maps, 64 samples) **11 s** |
| **Cycles** (fallback, or `render.engine:"cycles"`, or `VIDEO_ENGINE_3D_ENGINE=cycles`) | EEVEE unavailable (no EGL libs) | nothing extra (CPU path tracer) | draft (8 samples) 3 s, standard (24) 8.5 s, high (64) about 21 s; noisy, because the Debian build has no OpenImageDenoise |
| Workbench | measurements and asset thumbnails | nothing | 0.4 s |

- **Cycles GPU:** set `VIDEO_ENGINE_3D_DEVICE=GPU` to use OptiX, CUDA, HIP, oneAPI or Metal when present. It falls back to CPU silently, and the job's `ready` event reports the device used.
- **Blender startup:** about 0.8 s per job; GLB import about 0.2 s per model.
- **One process per render:** a video runs a single Blender process, so startup and import cost is paid once per video, not per frame.

## Research and prototype findings (before the schema was fixed)

| Question | Finding | Consequence |
|---|---|---|
| Backend | Blender headless covers GLB import (skins, clips, morph targets), cameras, lights and CPU rendering. three.js with headless-gl would need a WebGL stack plus our own skinning, shadows and lighting. | Blender as the only drawing backend. The engine keeps the scene and the timeline. |
| glTF importer | Needs `python3-numpy` with apt Blender. Takes about 0.2 s per model. | Documented dependency. |
| Clip names | Blender renames actions (`walk_Mika`), but the NLA tracks it creates keep the glTF animation names. | Clip map = `{track.name: track.strips[0].action}`. Clip durations come from our own GLB parser, so time mapping does not depend on Blender's fps. |
| Clip playback | We evaluate the action F-curves ourselves for a given clip time and weight. | Deterministic poses, exact per-frame control, and crossfades between clips. Quaternions are sign-aligned and normalised. |
| Bone parenting | `parent_type='BONE'` positions relative to the bone **tail**, and a `Child Of` constraint inherits armature scale. | Attached objects are placed per frame: world = bone deformation (posed · rest⁻¹) × the target's space × offset. They follow the bone through animation (verified to under 1 cm in tests). |
| Stray objects | The importer adds bone display shapes ("Icosphere"). | These are hidden from rendering. |
| Shape keys | Imported with their glTF names; unnamed targets become `morph_N`. | Morph names are the same in our parser and in Blender. |
| Axes | glTF is +Y up, Blender is +Z up. | A `WorldRoot` (+90° X) and a per-model "undo" (−90° X) keep every engine value in glTF convention. Camera and lights need no conversion, since both look along −Z. |
| Denoising | Debian's Blender has no OpenImageDenoise. | Denoise only when available. EEVEE is preferred. |
| EEVEE headless | Fails without `libEGL.so.1`. With Mesa EGL it runs through software GL. | Probe plus automatic Cycles fallback. |
| Units | Real-world assets vary. The Fox sample is centimetre-scale (about 100 units tall). | `asset_inspect` reports bind-pose bounds in metres, so agents set `scale` (Fox: 0.01). |

## Scene model

`scene_create {kind:"3d"}` creates a scene document with `kind: "3d"`:

```jsonc
{
  "kind": "3d", "canvas": {"width": 1280, "height": 720, "fps": 24, "background": "#000000"}, "duration": 96,
  "render": {"quality": "standard", "transparentBackground": false},   // engine?/samples? advanced
  "world":  {"color": "#c9d6e3", "strength": 0.6},                     // ambient light / background
  "camera": {"position": {"x": 0.4, "y": 1.5, "z": 3.2}, "lookAt": {"object": "mika", "bone": "head"}, "fov": 45},
  "lights": [{"id": "key", "type": "sun", "intensity": 2.2, "rotation": {"x": -50, "y": -35, "z": 0}},
             {"id": "fill", "type": "area", "intensity": 120, "position": {"x": 2.5, "y": 2.6, "z": 3}, "size": 2.5}],
  "objects": [
    {"id": "room", "asset": "room"},
    {"id": "mika", "asset": "mika", "clip": "walk", "position": {"x": -2.2, "y": 0, "z": 0.4}, "rotation": {"x": 0, "y": 90, "z": 0}},
    {"id": "cup",  "asset": "mug",  "attach": {"object": "mika", "bone": "rightHand"}, "position": {"x": 0, "y": -0.13, "z": 0.04}},
    {"id": "box",  "primitive": {"shape": "box", "size": {"x": 0.5, "y": 0.5, "z": 0.5}, "color": "#3366cc"}}
  ],
  "animations": [ {"target": "mika", "property": "clip", "keyframes": [{"frame": 0, "value": "walk"}, {"frame": 54, "value": "idle"}]} ],
  "audio": [], "overlay": {"scene": "title_overlay"}
}
```

- **Coordinates (glTF convention):**
  - metres; right-handed; +y up, +x right, +z toward the default camera;
  - models face +z, so `rotation.y` 90 faces +x (screen right) and 180 faces away;
  - rotations are in degrees, x applied first, then y, then z, about fixed axes.
- **Objects:** a model (`asset`), a primitive (`plane|box|sphere|cylinder`), or an empty group.
  - Box, sphere and cylinder stand on their position (origin at the bottom centre, like a character's feet).
  - `parent` means transform inheritance. A hidden parent hides its children.
- **Camera:** looks along its −z. `lookAt` can be a point or `{object, bone?}` and overrides `rotation`. `fov` is vertical, in degrees.
- **Lights:**
  - `sun` uses direction only (from `rotation`); `point`, `spot` and `area` are positioned;
  - lights shine along their −z;
  - intensity: sun in W/m² (typical 1–5), the others in watts (typical 100–2000).
- **Overlay:** a normal 2D scene with the same canvas size and fps, and a transparent background (`#00000000`), composited over each 3D frame. Titles, captions and infographics use the full 2D engine.

### Timeline (same operations as 2D)

| target | properties |
|---|---|
| object id | `position.x/y/z`, `rotation.x/y/z`, `scale.x/y/z`, `visible` (step), `clip` (step), `morph.<name>` (0..1) |
| light id | `position.*`, `rotation.*`, `intensity`, `color` (step) |
| `camera` | `position.*`, `rotation.*`, `lookAt.x/y/z` (animating these makes lookAt a point), `fov` |
| `world` | `strength`, `color` (step) |

**Clips.** The active clip is `clip`, overridden by a step `clip` track. `""` or `null` means none: the rest pose.

- Each change of clip starts a segment. Clip time restarts at `clipOffset`: `t = clipOffset + (frame − segmentStart) / fps × clipSpeed`.
- The time then wraps (`clipLoop`, default) or holds on the last pose.
- For `clipBlend` frames (default 8) the previous clip keeps playing and crossfades out.
- Clips play in place: move the object with position keys. `measure_layout` reports the active clips with their time and weight.

**Morph targets** are the facial foundation. Static `morphs: {smile: 0.5}` or `morph.<name>` tracks drive a model's blend shapes, so expressions and simple mouth shapes (open, "oh") can be keyed to narration timing. Full lip-sync is out of scope.

### Bones, sockets and attachments

`asset_inspect` lists a rigged model's joints and **sockets**. Sockets are semantic names detected from joint naming conventions: `rightHand`, `leftHand`, `head`, `neck`, `spine`, `chest`, `hips`, `root`, `rightFoot`, … For example `rightHand → hand.R`, or `b_RightHand_08` on the Fox.

`attach: {object, bone, follow}` makes an object follow that bone through every animation:

- `bone` is a socket or a joint name;
- `follow: "full"` follows position and rotation; `"position"` follows position only;
- the object's `position`/`rotation`/`scale` become offsets, expressed in the target character's own space at its rest pose and anchored at the joint;
- the attached object keeps its own scale.

## Inspection (the 3D `measure_layout`)

`measure_layout` on a 3D scene returns, per object at a frame:

- `world`: position (m), rotation (°, same convention as input) and scale, after parents and attachments;
- `bounds`: world AABB (min, max, size, centre) of the **evaluated** (animated, skinned) mesh;
- `screen`: projected pixel bounds (top-left origin, like 2D), `center`, `onScreen`, `fullyOnScreen`, `visibleFraction`, `depthMin`/`depthMax`;
- `cameraSpace`: `{x, y, depth}` of the object origin;
- `clips`: `[{name, time, weight}]`;
- `bones`: sockets or requested joints, each with world position, screen position, onScreen and depth;
- asset, primitive, parent and attach;
- plus the evaluated camera (position, rotation, forward, fov) and lights.

`render_preview {debug:true}` draws screen boxes, ids, clips, depth and hand/head/root sockets onto the frame, and returns the same measurement.

## Assets and cost

- **Formats:**
  - GLB, or `.gltf` with embedded (`data:`) buffers; external files are rejected, so a model is always one self-contained workspace asset;
  - skins, animations (unique names) and morph targets are read by a pure-TypeScript parser at import time, with no Blender needed.
- **Reuse:** a model is imported once and referenced by id from any number of objects and scenes. Byte-identical imports return the existing asset. Thumbnails are rendered once and cached. Every render is local CPU work, with no per-call API cost.
- **Test assets** (`assets/3d/`):
  - `character.glb` (rigged "Mika": 16 bones; clips idle / walk / wave; morphs smile, blink, mouth_open, mouth_oh);
  - `mug.glb`, `room.glb`;
  - all generated procedurally by `assets/3d/src/build_assets.py` (`npm run assets:3d`);
  - `third_party/fox/Fox.glb` (Khronos sample, CC0 model plus CC BY 4.0 rigging and conversion; see its `ATTRIBUTION.md`) shows that a real-world rig works too.

## Proofs

- **Core proof** (`npm run example:3d`, [`examples/3d-proof/`](../examples/3d-proof)): through the workspace API only, it
  - imports assets and builds a room scene;
  - makes the character walk in with the mug in the right hand, stop, turn, wave, smile and "talk" while the camera dollies;
  - adds audio and a 2D title overlay;

  - verifies mug-in-hand at 5 frames and renders `out/mika_3d.mp4` (5 s, 720p, audio).

  `out/report.json` lists 13 checks, all passing.
- **Agent proof over MCP:** a Tandem Builder agent does the same through the `video_engine_*` tools only; see [`tandem-e2e-3d/REPORT.md`](tandem-e2e-3d/REPORT.md).

## Limits (by design, or not yet done)

- **Out of scope:** text-to-3D, auto-rigging, IK, physics, cloth, photoreal rendering and full lip-sync.
- **Clips:**
  - they play in place; root motion is not extracted, so move the object with keys;
  - crossfades blend per channel (linear, quaternions normalised); there is no additive layering.
- **Attachments** follow one bone and keep their own scale. Hiding a character does not hide its attached props; hide those too.
- **EEVEE on software GL** has lower shadow resolution than Cycles. `quality:"high"` or `engine:"cycles"` trades speed for quality.
- **Performance:** 3D rendering is much slower than 2D (seconds per 720p frame on CPU), so long clips should use render jobs, which the MCP tools already do.
